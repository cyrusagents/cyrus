# Release decision: unpatched node-forge advisory

Observed October2 2026; source `23811dfadc78bf12549319435c4f94a81b79705b`.

## Exact blocker

`pnpm audit --audit-level low` reports exactly one HIGH advisory:
[GHSA-86w9-cpqp-85rv](https://github.com/advisories/GHSA-86w9-cpqp-85rv),
CVE-2026-85393. Affected node-forge <=1.4.0, no patched version listed; npm
latest is1.4.0. The defect accepts extra nested DigestAlgorithm elements during
RSA PKCS#1 v1.5 signature verification. GitHub reviewed the advisory October1.
The same direct dependency exists in published Cyrus0.2.73; PR1507 did not
introduce it. That does not exempt the new release from canonical checks.

`packages/edge-worker/package.json:55` declares `node-forge:^1.4.0`.
The lockfile resolves1.4.0. It is a direct dependency, so there is no patched
parent bump to pursue. No fixed registry version was found. The canonical
`release-cli.yml` build performs `pnpm audit --audit-level low`; it will reject
this payload unchanged before publication. Full output is retained in the CYPACK-1546 `rollout-gate-1002/audit.log` attachment; the coordinator independently reproduced exactly one HIGH advisory.

## Reachability inspection

The only direct shipping import is `packages/edge-worker/src/EgressProxy.ts:19`.
Search included all apps/packages source; test certificate helpers also import
forge but do not add a production call path.

- `generateCA` (line268): reads the existing local CA certificate and local
  private key, invokes `certificateFromPem` / `privateKeyFromPem`; otherwise
  generates an RSA2048 key, builds its own CA and signs SHA256. The new private
  key is stored mode0600. The code does not call certificate/public-key verify.
- `generateServerCert` (line335): generates RSA2048 key/certificate for the
  policy-selected hostname, signs it with the locally held CA, emits PEM.
  The hostname becomes subject/SAN data, not an input signature to verify.
- Forge1.4.0 implementation: `lib/x509.js:802` parses PEM/ASN.1 and calls
  `certificateFromAsn1`; it does not invoke signature verification. The
  returned certificate has a verify method, which Cyrus does not call.
- Upstream HTTPS uses Node's `https.request` with `rejectUnauthorized:true`
  (`EgressProxy.ts:745`). Node/OpenSSL performs TLS certificate verification;
  Cyrus does not route remote certificate verification through forge RSA.
- Normal tunnel connections are sockets; TLS termination server uses Node's
  HTTPS server and the generated PEM key/certificate.

**Conclusion limited to inspected source:** no path from an attacker-provided
signature to the affected forge RSA verification operation was found. This is
not a claim that forge1.4.0 is patched, that all possible future uses are safe,
or that audit passes. It does not justify silently suppressing the advisory.

## Required decision, no automatic workaround

Normal remediation is a vetted upstream fixed version, followed by the owning
direct dependency bump, locked install, zero-advisory audit, and relevant egress
TLS regressions. There is no such published version identified now, so no honest
release ETA can include publication until this dependency or policy decision is
resolved.

If the main operator elects to carry the documented risk for the scoped pilot,
that requires an explicit, narrowly reviewed policy/workflow decision with owner
and removal condition. None is authorized or implemented here. No advisory
ignore, audit-level change, fake version, vendor/fork substitution, crypto-system
replacement, or bypassed canonical publishing route is proposed as an automatic
fix. The feature candidate/release PR can be reviewed while publication is held.
